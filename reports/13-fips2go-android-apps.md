# 13. fips2go 活用法 — 「任意の Android アプリがメッシュの住人になる」価値の掘り起こし

対象アプリ: **fips2go**(`org.fips.android`,fr34aky/fips-android 系の配布名。
Zapstore 経由で入手可能な Android アプリ)

本レポートの問いはひとつ。**「デバイスではなく“アプリ”がメッシュに参加する」とは
何を可能にするか。** レポート 07〜12 が扱ったユースケースはすべて
「デバイス単位で網に入る」話だった(nvpn CLI、スマホアプリ、組込みノード)。
fips2go はその前提を一段下にずらす。選んだアプリだけが `fd00::/8` のメッシュ
IPv6 と `.fips` DNS を得て、選ばなかったアプリは網の存在さえ知らない。
この差分からしか生まれない活用を、なるべく nvpn(= nostr-vpn 製品群)では
出せない形で洗い出す。

---

## 0. 前提整理:fips2go が実際に何をするか(仕様メモ)

まず「何ができて何ができないか」を固めておく。
以降のユースケースの実現可否はすべてこの表に還元される。
(出典は Zapstore 掲載情報と fips-android の README に基づく。)

| 能力 | 内容 | ユースケース上の意味 |
|---|---|---|
| per-app スプリットトンネル | VpnService が選んだアプリの通信だけを捕捉する | 「このアプリだけ網に入れる/入れない」が選べる。網の参加単位がアプリ |
| 両スタック併存 | 捕捉されたアプリはメッシュとクリアネットの**両方**に届く | 「VPNに切替える」のではなく「メッシュが生える」。普段使いを壊さない |
| `.fips` DNS | 捕捉アプリの `.fips` 問い合わせは in-process で応答、それ以外は通常リゾルバへ | `ssh user@pc.fips`、`http://cam.fips` が既存アプリにそのまま通る |
| 既定拒否インバウンド | メッシュからの新規接続は既定で遮断。明示的なポート許可リスト + 自分が開いた接続の応答 + ICMPv6 のみ | スマホが「受け口」を持てるが、持つかどうかは自分で決める |
| Keystore 身元 | npub(=住所)が Android Keystore に封入、バックアップ/復元あり | 「住所が端末に宿る」。再インストールしても住所が生き残る |
| `!FIPS` ホットスポット | `!FIPS` という名前のオープン Wi-Fi に自動接続して近傍ピアと網を張る(普段の通信は元の経路のまま) | **インフラなし近接メッシュ**。SSID を立てるだけで会場・車内・避難所が網になる |
| mDNS LAN 発見(既定OFF) | 同一 Wi-Fi のピアを `_fips._udp` で見つけて直接ダイヤル | リレーを介さない LAN 速度の直結 |
| 移動耐性 | Wi-Fi↔セルラーの切替でセッションが ~20 秒で再ピンされて生き残る | 「動く住所」:移動中でも npub 宛に届き続ける |
| クリアネット転送 | 捕捉アプリの TCP/UDP はユーザースペースフォワーダで通常網へ出る | メッシュ非対応の普通の通信は普通に動く |

**できない/注意すべきこと**

| 制約 | 影響 |
|---|---|
| ブロードキャスト/マルチキャストはメッシュを横断しない | 「LAN 自動検出」頼みのアプリ(mDNS/UPnP/ブロードキャスト発見)は網上では機能しない。**手動で `ホスト名.fips` か `fd00::…` を打てるアプリ**であることが条件 |
| ポート許可リストは「網全体に開く」 | FIPS メッシュは許可不要の単一公開網(実測 ~1300 ノード)。許可したポートは「あなたの npub を知る全員」に届く。アプリ側の認証が必須 |
| ロースター/MagicDNS/サブネット/exit はない | nvpn の「承認された仲間だけの網」「出口ノード」「サブネット越え」は fips2go の守備範囲外。欲しければ nvpn と役割分担 |
| MTU 1280 | 大体の用途は問題ないが、ジャンボフレーム前提のプロトコルや極端なスループット用途は厳しい |
| 成熟度 | 本体も依存する FIPS も 0.x・監査なし。人命や金を直接預ける用途は避ける |

## 1. 「nvpn にない」を定義する — 4 つの差分ベクトル

nvpn と fips2go は同じ npub・同じメッシュ上の隣人だが、設計の重心が違う。
差分をベクトルにすると、どのユースケースが「fips2go でなければ」かが見える。

```
ベクトル1  粒度   nvpn: デバイス全体が網に入る(ロースター承認制のテイルネット)
                  fips2go: アプリ単位。網に入る面と入らない面を1台の中で切り分ける

ベクトル2  公開性 nvpn: 署名済みロースターの承認が要る“閉じた網”
                  fips2go: 許可不要の公開メッシュ。npub を知る誰でも(許可ポートに)届く

ベクトル3  近接   nvpn: インターネット越しの常時接続が主戦場
                  fips2go: !FIPS ホットスポット + mDNS で「その場にいる者だけの網」

ベクトル4  常駐   nvpn: 固定・デスクトップ的な常時ノードが主
                  fips2go: 移動する電話が第一級ノード(ハンドオーバーで壊れない)
```

このレポートで扱うケースは、どれかのベクトルが効くものに絞る。
逆に言えば「家族の全デバイスを一つの網で」みたいな話は nvpn の本領なので
ここでは扱わない(07/08/12 参照)。

### 補足: 「アプリがメッシュに参加する」とは技術的に何を意味するか

fips2go は Android の VpnService で「トンネルを張る」が、そこで流れるものが
従来の VPN とは違う。選んだアプリのパケットだけを TUN デバイスが吸い上げ、
`fd00::/8` 宛はメッシュに、その他はユーザースペースフォワーダ経由で
通常のネットワークに流す。つまり捕捉アプリから見える世界は

- 今まで通りのインターネット(Google、各種 CDN、LAN 内の機器)
- そこに「メッシュの住所空間」が**追加で見える**

という二重の世界。VPN の「切替える」ではなく「増える」ので、
スマホの普段の使い勝手を一切壊さずに、特定アプリだけに
「もう一つの網の扉」が生える。これが以降のケース全ての土台。

## 2. ユースケース群

以下、グループ別に。各ケースは「何をするか / 構成 / なぜ fips2go(=nvpn では出ない)
か / 注意点」の順で書く。グループは利用の「型」で分けた
(声 → スマホがサーバ → 既存アプリがクライアント → `!FIPS` 近接 →
端末再利用 → 隔離/セキュリティ → 遊び)。
各ケースの実現可否は第 0 節の仕様表に還元できるはずなので、
「本当に動く?」と思ったら第 3 節の適合性チェック、
第 7 節の FAQ、付録 B の検証状況を併せて見てほしい。

### A. 声・会話系 — 「サーバレス電話」

#### ケース 1: SIP 直結通話 — 電話会社も PBX も要らない電話

- **何をするか**: Linphone など SIP クライアントを入れ、相手を
  `sip:friend.fips`(あるいは `[fd00::…]`)で直接ダイヤルする。
  SIP サーバ(レジストラ)を経由しない**エンドポイント直打ち VoIP**。
- **構成**: 両端末に fips2go + SIP アプリ。相手側が「電話を受ける」側なら
  SIP アプリの待受ポート(5060/UDP 等)を fips2go の許可リストに登録。
- **なぜ fips2go か**: npub が電話番号になる、というのが本質。
  番号管理・課金・回線交換がない。「npub を知っている人にだけ
  鳴る電話」は SIP でも FIPS でも存在しなかった組合せ。
- **注意点**: SIP の RTP(音声本体)も UDP 直結になる。遅延はメッシュの
  経路依存(直結なら実用圏、多段中継なら品質低下)。UDP のメッシュ通過は
  実機で必ず検証すること。

#### ケース 2: Mumble/mumla — 常時接続の「隊内無線」

- **何をするか**: 片方(自宅PCや常設ノード)に murmur サーバを立て、
  スマホ側は mumla(Mumble クライアント)で `mumble://base.fips` に常時入室。
  サイクリング隊・フェス運営・山行・作業現場の「喋ったら届く」チャネル。
- **なぜ fips2go か**: 「網に入っているアプリだけが参加できる会議室」を、
  アカウント発行なしで実現。Discord 的な常時ボイスを完全自己ホスト化。
- **注意点**: murmur 側は PC か常設端末に置くのが現実的(スマホで
  サーバを持つことも理論上は可能だが、運用は重い)。

#### ケース 3: 「勝手に繋がる」インターホン — 実家↔自分の机

- **何をするか**: 実家に置いた古スマホと自分のスマホを、
  SIP 直結 or LAN トランシーバー系アプリ(手動 IP 接続ができるもの)で結ぶ。
  ボタンを押せば実家の台所に声が届く。
- **なぜ fips2go か**: 設定が「許可ポートを一つ開けて、相手の名前を
  覚える」だけ。高齢の親側に一切の運用を要求しないのが決定的に違う。
  nvpn だと「実家の端末をロースターに入れる承認運用」が先に来る。
- **注意点**: 相手が応答するまでの機構はアプリ側頼み(呼出音・自動応答
  の設定次第)。

### B. スマホが“サーバ”になる系 — ポケット公開サーバ

fips2go の許可リストを開けると、**スマホ上の普通のサーバアプリが
そのまま「npub 宛の公開サービス」になる**。承認不要の公開網なので
ロースター加入の交渉が要らない — これが nvpn との最大の違いで、
このグループはすべてこの差分で成り立っている。

#### ケース 4: ポケット Web サイト — 「あなたのサイトはあなたのポケットにある」

- **何をするか**: Simple HTTP Server / KSWEB / Termux の
  `python -m http.server` などで静的サイトをホストし、
  そのポートを許可リストに登録。アドレスは `http://あなた.fips:ポート`。
- **具体例**: 結婚式・学会・即売会で「撮った写真をその場で配る」。
  カメラマンのスマホが即席の配布サーバになる。QR コードで URL を配れば
  参加者のブラウザがそのまま見る(参加者側も fips2go が要る点は後述)。
- **なぜ fips2go か**: 「サイトがあなたと一緒に移動する」。会場を出ても
  セルラーに切り替わっても住所(npub)は同じまま — 移動耐性の実演でもある。
- **注意点**: 公開網なので、URL が知られれば誰でもアクセスできる。
  パスに推測不能なトークンを含める等の古典的防御を併用する。

#### ケース 5: Termux sshd — ポケットの Linux ボックス

- **何をするか**: スマホの Termux で `sshd` を起動(既定 8022)、
  fips2go の許可リストに 8022 を登録。ラップトップから
  `ssh -p 8022 user@phone.fips`。
- **できること**: リモートでスマホのファイル操作、`git` を入れれば
  **スマホを git リモート**にできる(`git push phone:~/repo`)、
  Termux 内の cron 的な定期処理の管理、スマホ上の写真・メモの吸い上げ。
- **なぜ fips2go か**: 「スマホが SSH 到達可能な端末」になる。
  SIM 抜きでも Wi-Fi さえあれば動く。
- **注意点**: sshd の鍵認証は必須(パスワード認証で公開網に出さない)。

#### ケース 6: IP Webcam — クラウドアカウント不要の防犯・見守りカメラ

- **何をするか**: 古スマホや普段のスマホに IP Webcam 系アプリを入れ、
  配信ポート(既定 8080)を許可リストへ。見る側は VLC やブラウザで
  `http://cam.fips:8080`。
- **用途**: ペット・赤ちゃん・空き家・車庫の見守り。
- **なぜ fips2go か**: 商用カメラの「メーカークラウドに映像を上げる」
  モデルを完全に回避できる。「npub を知る家族だけがアクセスできる
  カメラ」は、ポート開放も DDNS もクラウド契約も要らない。
- **注意点**: IP Webcam のパスワード/Basic 認証を必ず有効にする
  (許可ポートは網全体に見える)。

#### ケース 7: ポケットラジオ局 — 自分の音楽を自分から配る

- **何をするか**: スマホ内の音楽ライブラリを HTTP/DLNA サーバアプリで
  公開し、友人が VLC で `music.friends.fips` を聴く。あるいは自分の
  ポッドキャスト原稿読みを「その場ラジオ」として垂れ流す。
- **なぜ fips2go か**: ストリーミング事業者・プラットフォーム・
  アップロード行為がいっさい介在しない「私的放送」。
  `!FIPS` ホットスポットと組み合わせると**電波法的な意味での放送とは別物の
  「その場にいる人だけの局」**が作れる。
- **注意点**: 著作権のある楽曲を不特定に流す用途には使わない
  (私的範囲/自作コンテンツ向け)。

#### ケース 8: 「動くデモリンク」— 移動しながら生き続ける開発プレビュー

- **何をするか**: Termux で開発中の Web アプリ(code-server、
  `npm run dev`、自作 API など)を起動し、ポートを許可。
  `http://dev.fips:3000` を相手に渡す。
- **面白いところ**: 勉強会の会場を出て電車に乗っても、相手側から見える
  リンクが**切れない**。Wi-Fi→5G のハンドオーバーで ~20 秒再ピンされて
  追従する。「デモの間だけ存在する URL」が移動する実演になる。
- **なぜ fips2go か**: ngrok 的な「一時公開」だが、外部のトンネル
  サービスを挟まず、あなたの npub に直結している。

### C. 既存アプリがそのままクライアントになる系

このグループの本質は「**アプリ側は何も知らない**」こと。
`ホスト名.fips` や `fd00::…` を手動で打てるアプリは、全部そのまま
メッシュのクライアントになる。Android の巨大な既存アプリ資産が
無改造で使えるのは fips2go 固有の強み(デスクトップの fips デーモンでは
「ブラウザに入れる」等の統合が必要)。

#### ケース 9: DAVx⁵ — インターネットを一度も通らない連絡先・カレンダー同期

- **何をするか**: 自宅の Radicale/Baikal/Nextcloud を `dav.home.fips`
  で DAVx⁵ に登録。スマホの連絡先・カレンダーがメッシュ内だけで同期する。
- **なぜ価値か**: PIM(個人情報)の同期が「自宅→スマホ」の経路を
  外に一度も出さない。Google アカウントに載せない私的 PIM の実用形。
- **注意点**: サーバ側は自宅PCに fips デーモン or nvpn。

#### ケース 10: ntfy / Gotify 自前サーバ — FCM を通さないプッシュ通知

- **何をするか**: 自宅に ntfy サーバを立て、スマホの ntfy アプリの
  サーバを `http://ntfy.home.fips` に変更。家族・自作 IoT・サーバ監視の
  通知が Google の FCM を経由せず届く。
- **面白いところ**: 「家族専用の通知バス」。自宅の自作センサーが
  鳴らす通知、bash の `curl -d` 一発でスマホに届く自作通知系。
- **注意点**: ntfy アプリのフォアグラウンド常駐設定は要チューニング。

#### ケース 11: 閉域メッセンジャー — Element+Synapse または Conversations+Prosody

- **何をするか**: 自宅か常設ノードに Synapse(Matrix)や Prosody(XMPP)
  を立て、スマホ側クライアントのホームサーバ/接続先を `chat.home.fips` にする。
- **なぜ fips2go か**: 「公開網に登録しないメッセンジャー」。
  サーバがメッシュ上にしか存在しないので、外部にアカウントも通信経路も
  漏れない。家族・研究会・秘密度の高い相談コミュニティ向き。
- **注意点**: サーバ運用の手間はある。まずは XMPP(軽い)から試すのが現実的。

#### ケース 12: MGit 等の git クライアント — `git@nas.fips` への直 push

- **何をするか**: スマホの git クライアント(MGit 等)で
  `ssh://git@nas.fips/~/repo.git` に push/pull。自宅の git サーバや
  Termux の git-daemon を直接叩く。
- **なぜ fips2go か**: GitHub を経由しない私的リポジトリの往復が、
  スマホから直接できる。出先の電車で自宅のリポジトリにメモを push する。

#### ケース 13: リモートデスクトップ系 — bVNC / aRDP / Moonlight

- **何をするか**: VNC/RDP/GameStream クライアントで `pc.fips` に接続。
  特に Moonlight はホストを手動 IP 指定できるので、自宅 PC の
  GameStream に出先から繋がる可能性がある。
- **なぜ fips2go か**: 自宅 PC に nvpn を入れなくても、PC 側が生の fips
  デーモンか nvpn で `pc.fips` になっていれば届く。「リモートデスクトップの
  到達手段」を VPN 製品ではなく網そのものにする。
- **注意点**: Moonlight/GameStream のペアリング手順が複数ポートを
  要求するため、実機検証が要る。遅延は経路次第。

#### ケース 14: ゲーム — 「ホストはポートを開けなくていい」

- **何をするか**: LAN 対戦/ホスト接続型のゲームで、相手の `.fips` 名か
  `fd00::…` を手動で打つ。
- **候補(手動 IP/ホスト名を指定できるもの)**:
  - Minecraft(Java版はホスト名指定可。Termux でスマホ側にサーバを
    立てる荒技もあり)
  - OpenTTD(Android 版はサーバ IP 手動追加あり)
  - RetroArch netplay(ホスト側の `fd00::…` に接続)
  - PPSSPP adhoc(携帯同士でホスト/参加ができる)
- **なぜ fips2go か**: 「友達と遊ぶためのポート開放」という
  ネットゲーム最大の摩擦を消す。ホスト側の npub だけわかればいい。
- **注意点**: IPv6 を受け付けないゲームエンジンは不可。
  UDP 系の実機確認が前提。

#### ケース 15: KDE Connect — 出先でも「同じ部屋にいる」連携

- **何をするか**: KDE Connect は自動検出(マルチキャスト)が主だが、
  「デバイスを IP で追加」できる。自宅 PC の `pc.fips` を登録すれば、
  出先でも通知同期・ファイル転送・クリップボード共有が動く。
- **なぜ fips2go か**: LAN 前提の連携が「見えない LAN」の上に載る。
  「スマホと PC が同じ部屋にある」状態を距離無関係に再現する。
- **注意点**: マルチキャストは通らないので手動 IP 登録必須。

#### ケース 16: LAN 型ファイル転送(LocalSend / primitive ftpd 等)

- **何をするか**: LocalSend 系の「ローカルデバイス間転送」アプリ、
  あるいは primitive ftpd / HTTP サーバ系で端末間を直接結ぶ。
  「その場にいなくても AirDrop 的に届く」端末間転送。
- **構成**: 片側が受け側(転送アプリの待受ポート or ftpd)を許可リストへ。
  送る側は相手の `.fips` 名/`fd00::…` を手動で指定。
- **なぜ fips2go か**: 「手元のスマホ→遠くのスマホ」の直送を、
  クラウドの一時アップなしに行う。写真・ログ・録音の受け渡し。
- **注意点**: LocalSend 等は発見にマルチキャストを使うため、
  手動 IP 指定・「リンクで共有」的な逃げ道があるかをアプリ側で確認。

#### ケース 17: Tasker / MacroDroid — 「電話から電話への自動化」

- **何をするか**: Tasker の HTTP Request アクションで
  `http://grandma.fips/lamp` や `http://home.fips/gate` を叩く。
  スマホの状態(位置・時間・バッテリー)をトリガに、別の npub 宛に
  処理を飛ばす。
- **面白いところ**: 「スマホが起こす家の動作」「親のスマホに灯りを
  つける」など、クラウド連携サービスなしの個人自動化。
- **注意点**: 受け側は HTTP を受ける何か(自宅サーバ or 相手の
  スマホ側の待受アプリ)が要る。

### D. `!FIPS` ホットスポット系 — インフラなしの近接メッシュ

**ここが fips2go 最大の独自領域**。SSID が `!FIPS` のオープン Wi-Fi に
自動接続して近傍と網を張る、という仕掛けは nvpn にも fips デーモンにも
ない挙動で、「場所」をトリガにした即席網を可能にする。

#### ケース 18: 機内・車内・電車の「無インターネット網」

- **何をするか**: 誰かが機内モードのまま Wi-Fi ホットスポットを
  `!FIPS` という名前で立てる(あるいはモバイルルータ)。
  周りの fips2go が自動で網に入る。
- **できること**: 近距離のファイル受け渡し、LAN ゲーム、
  チャット(ローカルに立てた掲示板サーバ)。
  **インターネットが一切なくても成立する**のが決定的。
- **なぜ fips2go か**: そもそもインターネット前提の VPN では
  このシナリオは書けない。「その場の Wi-Fi 圏内だけが網」という
  位相は fips2go 固有。

#### ケース 19: イベント・学会・ハッカソンの「会場網」

- **何をするか**: 主催者が会場に `!FIPS` 名の AP を立てる。
  参加者の fips2go が自動で入り、会場限定のサービス
  (配布物サーバ、Q&A 掲示板、出欠名簿、デモ機一覧)に届く。
- **なぜ fips2go か**: 参加の手順が「Wi-Fi を見るだけ」で、
  会場側は AP を立てるだけ。Web 申込み・アカウント発行・
  会場のキャリア混雑を全部スキップできる。
- **注意点**: `!FIPS` はオープン Wi-Fi への自動接続機能なので、
  信頼できない場所で無闇に有効にしない(後述のセキュリティ節)。

#### ケース 20: 教室・合宿の「配布網」

- **何をするか**: 教員・リーダーが `!FIPS` AP を立て、
  教材サーバ(配布 PDF・提出箱・連絡板)をローカル公開。
- **なぜ fips2go か**: 学校のフィルタリング網やキャリア制限とは
  無関係に、「この部屋だけの教材網」が作れる。ネット未整備の
  合宿所でも成立する。

#### ケース 21: 災害・避難所の「掲示板網」

- **何をするか**: バッテリー駆動のルータに `!FIPS` SSID を立て、
  ローカルに掲示板/連絡先/物資リストの Web サーバを置く。
  避難者の fips2go が自動で網に入り、ブラウザで `board.shelter.fips` を
  見る。電力と Wi-Fi さえあれば ISP が死んでいても網になる。
- **なぜ fips2go か**: レポート 09 の災害網は「住民側は nvpn アプリ」
  としていたが、fips2go なら**任意のブラウザがそのまま住民側**になる。
  オンボーディングの最小化は災害用途では本質的な差。
- **注意点**: 通信の範囲は Wi-Fi 圏内(+その先のメッシュ)。大規模化は
  別途設計が要る。

#### ケース 22: 山小屋・キャンプ場の「お店網」

- **何をするか**: 山小屋の主人が `!FIPS` AP とローカルの
  「売店/天気/緊急連絡」ページを置く。宿泊者は部屋から見る。
- **なぜ fips2go か**: 電波の届かない場所こそ、この網が唯一の
  「デジタル掲示板」になる。

### E. 使い古し端末の再活用系

#### ケース 23: 引き出しの古スマホ = 常設メッシュノード

- **何をするか**: 使わなくなったスマホに fips2go を常駐させ、
  IP Webcam・HTTP サーバ・センサー公開などを任せる。
- **二つの価値**:
  1. **自分向け**: 無料の常設ノード・カメラ・ミニサーバ。
  2. **網向け(利他)**: ルーティング参加でメッシュそのものを太くする。
     「古い端末をメッシュの木にする」という再利用の思想。
- **注意点**: 常時稼働の発熱・電池劣化管理。信頼できる場所に置く。

#### ケース 24: 車載スマホ

- **何をするか**: 車に常置する安い端末に fips2go + GPS/カメラアプリ。
  駐車中のチェックイン、車載カメラのライブ/録画、`!FIPS` 圏内に
  入ったときの「着いた」通知。
- **注意点**: 車内温度での電池リスク。端末の物理保護。

#### ケース 25: 子ども/祖父母への「見守り端末」

- **何をするか**: 渡す端末に fips2go を入れ、**特定アプリだけ**を
  メッシュに参加させる。カメラ・位置・SOS 的なアプリだけが網に住み、
  ゲームやブラウザは網を知らない。
- **なぜ fips2go か**: per-app 粒度が「渡す端末の安全」を担保する。
  全部入りの VPN ではこの切り分けはできない。
- **注意点**: 相手(子供・高齢者)のプライバシーと合意の範囲に配慮。

### F. セキュリティ・隔離の活用

#### ケース 26: 「メッシュ専用ブラウザ」で網の住み分け

- **何をするか**: メインとは別のブラウザ(Firefox Klar、Brave の
  別インストール等)を入れ、それ**だけ**を fips2go の対象にする。
- **得られるもの**:
  - メイン環境は `.fips` を一切解決しない → 「変な URL を踏んで
    内部サービスに飛ばされる」系の事故を構造的に遮断。
  - メッシュ用ブラウザは clearnet にも出られるので、
    「表の Web」と「網の中」を1台で持てる。
- **なぜ fips2go か**: デバイス全体が網に入るモデルでは、
  全アプリが `.fips` を解決してしまう。アプリ単位の対象指定だから
  この「隔離された窓」が作れる。

#### ケース 27: 「機密アプリだけ網に」の最小権限

- **何をするか**: 網に触れるべきアプリ(自宅管理アプリ、SSH、
  仕事のメッシュツール)だけを対象にし、SNS・ゲーム・決済系は
  一切対象にしない。
- **なぜ価値か**: 「網に触れる面」を最小化することで、
  悪意あるメッシュピアや誤った `.fips` リンクが触れられる
  アプリ面を減らす。公開網だからこそ、入口の最小化が意味を持つ。

#### ケース 28: 「表の Web」と「網の内側」の1台同居

- **何をするか**: 同じスマホで、あるアプリ群は clearnet、
  別のアプリ群は clearnet+mesh に住まわせる。
- **面白いところ**: 端末が「二つのネットワークの境界」になる。
  普段のブラウザは普通の Web、別アプリは `.fips` の世界 — 
  網の出入りをスワイプで切り替える感覚。

### G. 実験・面白系

#### ケース 29: スマホが背負う webring

- **何をするか**: 仲間内で各自のスマホが自分のホームページを
  ホストし、互いの `名前.fips` をリンクする小さな輪。
- **なぜ面白いか**: 「ページは持ち主のポケットにある」という
  物理感。誰かが圏外になればその人のページも消える、という
  Web にはない性質を遊びとして楽しめる。

#### ケース 30: 「移動する住所」の実演

- **何をするか**: 自分の npub 宛の何か(Web ページ、ストリーム、
  SSH セッション)をぶら下げたまま電車や車で移動し、相手側から
  見えるリンクが切れないことを見せる。
- **なぜ面白いか**: 「住所は場所ではなく鍵である」という
  FIPS の本質が、体感として伝わるデモになる。

#### ケース 31: ポケット dead drop — その場限りの交換所

- **何をするか**: イベントや旅先で、その場だけの一時的な
  ファイル交換サーバをスマホに立て、終わったら消す。
- **なぜ fips2go か**: アカウント・登録・クラウドの痕跡が要らない。
  網に現れて、網から消えるだけ。

## 3. どのアプリが「メッシュに住める」か — 適合性の見極め

fips2go の万能性は「無改造アプリが使える」にあるが、無条件ではない。
網上で機能するかどうかはアプリ側の接続方式で決まる。
試す前の見極めは次の4点。

| チェック | 質問 | 例 |
|---|---|---|
| 手動接続できるか | ホスト名・IP・ポートを**自分で打てる** UI があるか | ssh/HTTP/FTP/サーバIP入力のあるゲーム=OK。「近くのデバイスを自動検出」だけのものは不可 |
| IPv6 を受け付けるか | 相手先が `fd00::…` または `.fips` 名(AAAA)で通るか | ほぼ全てのネットワークアプリは通るが、一部の古いゲーム・埋め込み IPv4 前提のものは不可 |
| ブロードキャストに頼るか | 発見機構が mDNS/UPnP/ブロードキャストのみか | 頼るものは網上では見えない(手動指定の逃げ道があれば OK) |
| 待受ポートを明示できるか | 自分が「受ける」側なら、待受ポート番号が決まっているか | 固定ポート=許可リストに書ける。動的・範囲が広いものは不向き |

**ざっくり言うと**:
- **強い適合**: ssh/HTTP/FTP/git/DAV/VNC/SIP/Mumble/手動 IP 指定のあるゲーム
- **条件付き**: 自動検出+手動指定両対応のもの(KDE Connect、一部カメラアプリ)
- **不向き**: ブロードキャスト依存・クラウドアカウント前提・IPv6 非対応のもの

### 「受け側」と「発信側」の非対称を理解する

fips2go で混乱しがちなのは「どちらが網に参加する必要があるか」だ。
整理すると:

| 側 | 何が必要か | 理由 |
|---|---|---|
| 発信(あなたのアプリ→相手) | アプリを fips2go 対象にする | `fd00::/8` 宛の送信と `.fips` 解決が要る |
| 受け(あなたのスマホで待受) | **許可リストにポートを登録するだけ** | スマホのノード自体が網の端点。アプリは対象に入れなくても届く |

つまり「スマホのサーバアプリを公開する」場合、そのサーバアプリを
fips2go の対象アプリにする必要すらない — 必要なのはポート許可だけ。
この非対称を押さえると、B 群(ポケットサーバ)の設定が一気に楽になる。

個別ケースより強いのは、それらを一つの生活・場面に束ねた形。
実際に意味を持つ組合せをいくつか挙げる。

### シナリオ α: 「出先の私」と「家の中」を1枚の網に

- **構成**: 自宅PC(生 fips or nvpn)+ スマホ fips2go。
- **束ねるケース**: C-9 DAVx⁵ + C-10 ntfy + C-12 git + A-1 SIP。
- **できあがるもの**: 連絡先・カレンダーは自宅にだけ置き、通知は
  FCM を通さず、git は自宅サーバに直接、緊急時は SIP で自宅に電話。
  **「家がサービス提供者、スマホが住民」の完全自己ホスト生活。**

### シナリオ β: 見守り端末セット

- **構成**: 実家に置く古スマホ + 自分のスマホ(両方 fips2go)。
- **束ねるケース**: E-25 + B-6 + A-3。
- **できあがるもの**: 実家の台所に置いた端末がカメラ・インターホン・

### シナリオ γ: イベント運営パック

- **構成**: 主催者の `!FIPS` AP + 主催者スマホの HTTP サーバ。

- **できあがるもの**: 会場限定の「配布物・Q&A・連絡網」。
  参加手順が「Wi-Fi 名を見る」だけ。

### シナリオ δ: 車・移動体

- **構成**: 車載古スマホ + 自分のスマホ。
- **束ねるケース**: E-24 + B-6 + D-18。
- **できあがるもの**: 駐車中の見回りカメラ、帰ってきたときの

## 5. すぐ試せる3レシピ

### レシピ A: ラップトップ → スマホの Termux SSH(最短で「届く」を体感)

1. スマホ: Termux で `pkg install openssh` → `sshd`(8022 で待受)
2. fips2go: 許可ポートに **8022** を追加 → Termux は対象アプリに
   **入れなくてよい**(サーバ側は網に「参加」しなくても TUN を越えて届く
   — 正確には「スマホ自体が網の端点」なので許可リストが効く)
3. 自分の npub を Diagnostics で確認 → `phone.fips` 的な名前として
   ラップトップ側(生 fips or nvpn)で `ssh -p 8022 u0_aXXX@<phone の npub>.fips`
   または `fd00::…` 直打ち
4. `ssh` が通れば、スマホは「npub 宛の Linux ボックス」

### レシピ B: 見守りカメラ(IP Webcam)

1. 古スマホ or 普段のスマホに IP Webcam → 配信開始(既定 8080)
   **パスワード認証を必ず有効化**
2. fips2go 許可リストに 8080
3. 見る側(fips2go 側でブラウザ/VLC か、デスクトップ fips):
   `http://<そのスマホの npub>.fips:8080`

### レシピ C: `!FIPS` 会場網の最小実験

1. 誰か1人がスマホの Wi-Fi テザリング/モバイルルータの SSID を
   `!FIPS`(パスワードなし)にして立てる
2. 他の fips2go が自動で近傍網に入る(自動接続を有効にしている前提)
3. 誰かのスマホに HTTP サーバ + 許可ポート → `http://host.fips:PORT` を
   その場で共有 → インターネットなしの会場網が完成

## 6. 注意点と「やらないほうがいいこと」

| 注意 | 内容 |
|---|---|
| 許可ポートは「公開網に開く」 | npub を知る誰でも到達できる。アプリ側認証(パスワード/鍵)なしにポートを開けない |
| 自動検出は通らない | mDNS/UPnP/ブロードキャスト頼みのアプリは網上では見えない。手動で `.fips` 名/`fd00::` を打てるものを選ぶ |
| `!FIPS` の無差別自動接続 | 見知らぬ `!FIPS` AP は「誰でも立てられる」。空港・街中での無闇な有効化は避け、使う場面だけ ON にする運用が安全 |
| 成熟度 | 0.x・監査なし。命・金・責任が直接かかる用途にはしない |
| 電池 | 常時ノードは電池を食う。古スマホ常駐は冷却・バッテリー劣化に注意 |
| nVpn の出番を奪わない | ロースター管理・MagicDNS・subnet・exit が要る用途は nvpn の本領。fips2go は「アプリ単位」「公開網」「近接」で住み分ける |

## 7. FAQ — 試す前につまずきそうな点

**Q. 相手側も fips2go が要るの?**
A. 要るものと要らないものがある。`.fips` 名を解決して届くには、相手側も
「メッシュの住民」でなければならない(fips2go、デスクトップの fips
デーモン、nvpn のどれか)。逆にこちらが受ける側なら、相手は普通の
「メッシュ上の誰か」でよい。どちらにせよ「網の外の人」には届かない — 
それがこの網の定義でもある。

**Q. `.fips` ってどんな名前になるの?**
A. ノードの npub がそのまま住所になる(`npub1….fips`)。fips2go は
config 内の既知ピアに別名を割り振れるので、`friend.fips` 的な読みやすい
名前で届く(別名は自分のローカルな付け方であり、網上の公式名ではない
点に注意)。

**Q. 「スマホにサーバを立てる」と公開網に晒されるのでは?**
A. その通り — 許可リストに書いたポートは npub を知る全員に届く。
だから「アプリ側の認証(鍵/パスワード/トークン付き URL)」は必須。
ただし「全世界の誰でも」ではなく「メッシュにいる誰か」ではある。
それでも公開と心得て防御すること。

**Q. 電池は持つの?**
A. 実測値では battery_saver 有効時にアイドル CPU が数 ms/s・起きる回数が
~7.5/s 程度まで絞られる報告がある(実機・条件依存)。常時ノード運用は
試せるが、「寝てる間ずっと受け付けたい」系は電池と相談。古スマホ常駐は
発熱・劣化に注意。

**Q. nvpn と併用できる?**
A. 同じ npub・同じメッシュ上なので論理的には併用できる。
役割は住み分けるのが綺麗 — 「仲間内の閉域網・出口・subnet」は nvpn、
「アプリ単位・公開網・近接」は fips2go。同じスマホで両方動かす場合は
VpnService が1つしか取れない点だけ注意(同時起動は要確認)。

**Q. 本当にインターネットなしでも動く?**
A. `!FIPS` ホットスポットや mDNS LAN 発見の範囲では動く
(その場の Wi-Fi 圏内での網)。ただし「グローバルなメッシュ」に出るには
何かしらの IP 到達性が要る — Nostr リレー越しの advert・ピアへの直結が
初回の出会いの仕組みだからだ。完全オフラインでは「その場限定の網」に留まる。

**Q. 友達に「.fips のリンク」を送っても開けないのはなぜ?**
A. その友達の側にメッシュがないから。`.fips` は特別な TLD ではなく、
fips2go がアプリごとに解決する内部名。「リンクを送る」より先に
「友達にも fips2go を入れてもらう」が前提になる。

## 8. まとめ — 「fips2go でなければ」の条件と推奨の優先順位

fips2go の本質は「**アプリが網の住民になる**」こと。
だから価値があるのは次のどれかが効く場面だ。

1. **アプリ単位の隔離**: 網に触れる面を選ぶ(見守り端末・専用ブラウザ・最小権限)
2. **公開網での受け**: npub を知る誰でも到達できる(ポケットサーバ・配布・公開)
3. **`!FIPS` の近接**: 場所をトリガに網が生える(会場・機内・避難所)
4. **移動する住所**: ハンドオーバーで壊れない常時ノード(動くデモ・車載)

特に「スマホがサーバになる系(B)」と「`!FIPS` の近接網(D)」は
nvpn にはない領域であり、かつ「既存の Android アプリが無改造で
使える」という fips2go 固有の強みが最も出る場所だ。

### 個人的な推奨の優先順位(実現容易さ × 面白さ)

| 順位 | ケース | 理由 |
|---|---|---|
| 1 | B-4 ポケット Web サイト | セットアップが最も軽く、「あなたのサイトはポケットにある」体験が強い |
| 2 | D-19 会場網 | `!FIPS` の独自性が最も出る。合宿・勉強会で即試せる |
| 3 | B-6 見守りカメラ | 実用性が高く、クラウド不要のカメラは価値が伝わりやすい |
| 4 | A-1 SIP 直結 | 「npub が電話番号」は強いが、実機検証の手間がある |
| 5 | C-9 DAVx⁵ PIM 同期 | 地味だが「Google に載らない私的同期」の実用形 |

どれか一つでいいので、まずは「スマホの許可ポートに何かを開けて、
別の端末から `.fips` で届く」体験を掴むのが最短の理解経路だ。
そこから先は、自分の生活・持ち場・遊びに合わせて
「どのアプリを網の住民にするか」を選ぶだけ — それが fips2go の
発想の転倒であり、nvpn にはない楽しさの芯だ。

### 追補(2026-09-25): エミュレータ + fips デーモンでの実測

Android エミュレータに fips2go v0.7.0 と各アプリを入れ、ホスト側の fips デーモン
(TUN `fips0`、メッシュ IPv6 `fd72:…`) とピアリングして実際に繋いだ結果。
「そのアプリに IPv6/ホスト名を手で打てるか」が各ケースの成否を分ける。

| アプリ | 手動で指定できるもの | メッシュ越しの実測結果 | 判定 |
|---|---|---|---|
| mumla(ケース2 Mumble) | サーバ Address + Port | murmur 1.3.4 に `home.fips:64738` で接続 → TLS ハンドシェイク → 認証 → チャンネル入室まで全行程成功(サーバ ping 12ms、バージョン表示も取得) | ◎ 成立 |
| ntfy(ケース10) | カスタムサーバ URL | `home.fips:8081` の自鯖 ntfy に publish → 配信まで成功 | ◎ 成立 |
| Linphone(ケース1/3 SIP) | SIP ドメイン + トランスポート(UDP/TCP) | `home.fips` 宛ての `REGISTER` がメッシュ越しにホストへ届き 200 OK まで往復。**SIP シグナリング自体は通る**。ただし通話(INVITE)はエミュレータでは発射されず(音声/ICE 周りの可能性が高く、エミュレータ特有の問題か)。受話側も IP:ポート直打ちでは鳴らず | △ 信号のみ実証、通話は実機要確認 |
| LocalSend(ケース16) | Favorites「Add」の IP Address + Port | **IPv6 リテラルがそのまま入力可**。登録時にメッシュ越しで `POST /api/localsend/v2/register` が届き、相手情報(端末名「MeshHost」・機種)を取得して Favorites に表示。マルチキャスト発見はメッシュを越えないので Nearby devices からは見えないが、favorite 経由なら到達する。ファイル本体の転送は簡易受信側の応答不足で未完 | ○ 手動 IPv6 + メッシュ到達は確認、転送は実機同士で要確認 |
| primitive ftpd(ケース16) | 受信側(スマホ)のポートを「Inbound firewall」許可リストへ | SFTP セッション確立(ログイン・転送)成功。FTP 受動モードはデータポート(5678)を許可し忘れるとハング → 受動ポート範囲の許可 or SFTP 推奨 | ○ 成立(要ポート設定) |
| Conversations+Prosody(ケース11) | 未実測 | 未実測。構造上は有望: Conversations はアカウントの domain と接続先 host/port を別指定でき、平文 TCP 5222 があるため `.fips`/IPv6 直結が効きやすい | △ 調査ベース |
| Element+Synapse(ケース11) | 未実測 | 未実測。構造上は不向き: Element は homeserver URL に HTTPS(正当な証明書)を要求し、`.fips` 向けの信頼できる証明書は取れない。自己署名を通す実用ルートがないため、閉域メッセンジャーは Conversations+Prosody 側が現実的 | △ 調査ベース(不利) |

**「IPv6 で手動セットできるものばかりなの?」への答え:**

- **手動で IPv6/ホスト名を打てるもの(→使える)**: mumla(サーバ Address+Port)、LocalSend(Favorites の IP+Port — IPv6 リテラルで確認)、ntfy(カスタムサーバ URL — ホスト名可)、Linphone(SIP ドメイン)、primitive ftpd 等のサーバ系(bind するアドレス + fips2go 側のポート許可)。
- **手動指定が弱い/できないもの(→そのままでは厳しい)**: Element(HTTPS 必須のため `.fips` 向け証明書が無理)、マルチキャスト発見だけに頼るアプリ(メッシュ越しの発見は効かない — LocalSend も discovery は通らないが favorites の手動登録という逃げ道がある)。アプリによっては接続先を「検出から選ぶしかない」ものがあり、そこは実際に開いて試すしかない。
- **もう1つの落とし穴**: `.fips` DNS は AAAA(IPv6)しか返さない。IPv4 の A レコードしか引かないアプリは名前解決で死ぬので、**IPv6 リテラル直打ちが最も確実な指定方法**。

検証環境: エミュレータ側 npub `npub1l7aph…`(fd5d:…:f127)、ホスト側 `npub1hl0dnkk…`(fd72:…:8837)。fips2go の Battery saver は既定 ON でリンクが切れやすいため、実測時は OFF を推奨(実機でも長時間接続なら同じ落とし穴がある)。

### この先の検証で伸ばしたいケース

レポートとして次にやる価値が高いのは、**B 群(ポケットサーバ)と
D 群(`!FIPS` 近接)の実機検証**だ。特に

1. 許可ポート経由でスマホ上の HTTP サーバに外部ノードから届くか
2. `!FIPS` SSID 自動接続がどの Android バージョン/端末で機能するか
3. SIP/Mumble 等の UDP 音声がメッシュ上で実用品質になるか

この3点は「nvpn にはない」価値の心臓部であり、白黒をつける優先度が高い。

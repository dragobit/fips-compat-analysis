# 06. FIPS とは何か — 俯瞰的・超大作レポート

> 「そもそも fips とは何なのか」「どんなことができるのか」を、この技術だけに
> とらわれない視点で分析する。対象は jmcorgan/fips と mmalmi 系フォークを
> ひっくるめた「FIPS というプロトコル/思想」そのもの。

---

## 第1部 FIPS の本質 — 3文でいうと

1. **「公開鍵がそのまま住所になるネットワーク」**。Nostr の鍵対(npub)が
   ノードのルーティングアドレスであり、暗号セッションの相手であり、
   アプリケーションのエンドポイントでもある。IP アドレス、DNS、証明書
   発行局、ユーザー登録 — 既存インターネットの「誰かに割り当ててもらう
   識別子」がすべて不要。
2. **「何でも運ぶメッシュ」**。UDP/TCP(インターネット上のオーバーレイ)から
   素の Ethernet・Wi-Fi・Bluetooth・Tor onion・Nym・(mmalmi 系は)WebSocket/
   WebRTC まで、パケットが運べるものなら何でもトランスポートにする。
   ルーティングはスパニングツリー座標 + ブルームフィルタ誘導で、
   グローバルなルーティングテーブルを持たない。
3. **「二重に暗号化された届け物」**。ホップごとに Noise IK(リンク層 FMP)、
   エンドツーエンドで Noise XK(セッション層 FSP)。中継ノードは
   「誰に届けるかの座標」だけを知り、中身と端点の身元は読めない設計。

## 第2部 技術史における位置づけ — どこから来て、どこへ行くのか

FIPS は新しい暗号や新しいルーティング理論を発明したわけではない。
公式文書(`fips-prior-work.md`)自体が認める通り、**実績ある部品を Nostr 時代の
文脈で組み直した合成品**である。以下の系譜をたどると何をやっているかが明瞭になる。

### 系譜 1: cjdns → Yggdrasil → FIPS(暗号アイデンティティ = 住所)

- **cjdns (2011~)**: 公開鍵のハッシュから IPv6 アドレスを導出し、
  「アドレス割当機関なし」でメッシュを張る先駆け。暗号=身元の思想を確立。
- **Yggdrasil (2018~)**: cjdns の非構造メッシュに対し、**単一スパニング
  ツリー + ツリー座標**による貪欲(greedy)ルーティングを導入。
  ノードは自らの「ルートからの経路」を座標として保持するだけで
  全メッシュへ届く。FIPS のルーティングはこの v0.5/Ironwood の直接の継承。
- **FIPS の新規性(この系譜での)**: Yggdrasil のアイデアを
  「トランスポート抽象 + Nostr アイデンティティ + ブルームフィルタ誘導の
  座標発見」で再構成し、リンク品質メトリクス(ETX+SRTT)による
  コスト感応型の親選択・フラップ抑制を独自に追加した点。

### 系譜 2: STP/RIP/Babel → FIPS(古典分散ルーティングの応用)

- **IEEE 802.1D STP (1985)**: 最小 ID がルートを選挙するだけで全ネットに
  ツリーができる、という40年物の分散アルゴリズム。FIPS はこれを
  Ethernet ブリッジの文脈からオーバーレイメッシュに移植。
- **RIP/Babel のスプリットホライズン**: 「教えてくれた相手には教え返さない」
  ルールを距離ベクトルではなく**ブルームフィルタ(確率的集合広告)に適用**。
- **ETX (De Couto 2003)**: 無線メッシュのリンク品質指標を OLSR/Babel から継承。

### 系譜 3: WireGuard/Lightning/Noise → FIPS(暗号化)

- **Noise Framework**: FMP=IK パターン(WireGuard と同じく、事前に相手の
  静的鍵を知っている前提で 1 ラウンドトリップ)、FSP=XK パターン
  (Lightning BOLT #8 と同じく、イニシエータの身元秘匿を優先して
  3 メッセージ)。ただし**独自方言**(レポート 02)である点に注意。
- **WireGuard の receiver index**: O(1) セッションディスパッチを踏襲。
- **DTLS のリプレイ窓、QUIC のスピンビット、RTCP の Sender/Receiver
  Report、IKEv2 の同時開始タイブレークと再起動検知、RFC1191 PMTUD**。
  要するに「インターネット標準の良いとこ取り」。

### 系譜 4: Tor/I2P → FIPS(だが目的は違う)

ホップバイホップ + エンドツーエンドの二層暗号、は Tor のオニオン構造や
I2P のガーリックルーティングと同型。**ただし FIPS は匿名ネットワークでは
ない**。中継ノードはエンドポイントの身元を原則知らないが、トラフィック
解析への対策(パディング、カバートラフィック、固定的回路)は入っていない。
「守るのは機密性と完全性であり、通信の存在や形状ではない」。

### 位置づけの結論

```
      アイデンティティ        ルーティング         暗号化        到達範囲
      -------------          ----------------   ---------     ----------
IP    割当(ICANN/RIR)         BGP/リンク状態      なし(上位層)    グローバル
cjdns pubkey hash IPv6       Kademlia DHT        常時          メッシュ内
Yggdrasil pubkey hash IPv6   ツリー座標+greedy    常時          メッシュ内
Tailscale WireGuard鍵+Coord  ハブ制御のP2P        WG            管理ドメイン
Reticulum pubkey             経路記録+フラッド    常時          マルチトランス
Tor/I2P .onion/鍵            リレー選択           多層          匿名性特化
FIPS  Nostr npub (16B hash)  ツリー座標+bloom誘導  2層 Noise     マルチトランス
```

FIPS は **「Yggdrasil のルーティング頭脳 + cjdns の暗号住所 + WireGuard/
Lightning の Noise 作法 + Nostr の PKI」**を一つの自律メッシュに束ねたもの。
ユニークなのは個々の要素ではなく、**「Nostr という既にユーザーが持っている
鍵と名声のレイヤを、そのままネットワークの PKI と住所台帳に転用した」**点。

## 第3部 何ができるのか — 機能を価値の順に並べる

### A. 既存インターネット「の上に」使う(オーバーレイモード)

1. **公開鍵だけで到達できるプライベートメッシュ**
   - NAT・CGN・ファイアウォール・ISP の外に「どの npub とも通信できる」
     オーバーレイを張る。UDP ホールパンチ + メッシュ中継で、
     到達不能な双方のピアでも経路を構成する。
   - 既存ソフトはそのまま: TUN アダプタが npub→`fd00::/8` を生成し、
     IPv6 ヘッダ圧縮して運ぶので SSH・HTTP・ファイル転送等が無改造で動く。
   - **Tailscale との最大の違い**: コーディネーションサーバがいらない
     (任意で Nostr リレーをディスカバリに使うだけで、ピア間の直接配布も可能)。

2. **ポート多重サービス(IPv6 不要のネイティブパス)**
   - FSP の DataPacket で「ポート番号 + 宛先 npub」に直接データグラムを送れる。
     IPv6 エミュレーションを介さないのでオーバーヘッドが小さい。
   - 本家には実験的なネイティブ・データグラム API(ローカルプロセスが
     ソケット風に使う)。**信頼性レイヤは現状存在しない**(本家は ROD を
     v2 予定と明記;mmalmi 系は上位に fips-tcp で TCP 相当を自作済)。

3. **マルチトランスポート合成**
   - 一つのノードが UDP+TCP+Tor+BLE を同時に持ち、上流を横断して
     ルーティングする。パケットは経路中で媒体を跨ぎ、アプリは意識しない。

### B. インターネット「の外で」使う(グラウンドアップモード)

4. **ISP・IP・DNS なしの完全自立ネットワーク**
   - 素の Ethernet / Wi-Fi / BLE のみでメッシュを張り、ノードが自動で
     IPv6 アドレスを得て既存ソフトが走る。OpenWrt では 802.11s ラジオを
     バックホールに、開放 SSID でスマホ/PC を無設定参加させられる。
   - 災害時・辺地・「検閲下でインターネットは使えない」状況の
     実用的な選択肢になる。

5. **ブラウザ・モバイルの参加(mmalmi 系のみ)**
   - fips-ts でブラウザが WSS シード経由でメッシュに参加、WebRTC で
     ブラウザ同士が隣接ピアになる。nostr-vpn はモバイル/デスクトップの
     製品としてこの上に VPN を出荷済。

### C. 経済・社会レイヤ(Nostr 連携の独自性)

6. **npub がそのまま商品住所になる**
   - nostr-vpn は既に「バイト計量の公開出口ノードを Cashu(Bitcoin ecash)で
     支払う実験的マーケットプレイス」を実装。FIPS の「鍵=住所=課金対象」が
     ここに効く。**Nostr が単なる SNS プロトコルではなく、ネットワークの
     PKI・ディスカバリ・レピュテーション・課金レイヤに化ける**。
   - kind 37195 advert(発見広告)も「誰が何を提供しているか」の署名付き
     台帳であり、Nostr リレーが人間向けと機械向けの両方のディレクトリに
     なりうる。

7. **ディスカバリとシグナリングの Nostr 化**
   - Nostr リレーは FIPS パケットを運ばず、署名付き advert(37195)と
     ホールパンチシグナリング(21059)のみを運ぶ。リレーがダウンしても
     メッシュ自体は死なない — **Nostr は bootstrap であって依存先ではない**。

### D. できないこと(正直な限界)

- **匿名性は提供しない**(Tor/I2P とは設計目的が違う)
- **信頼バイトストリームは本体にない**(TCP 層は fips-tcp かアプリ責任)
- **グローバルスケールへの証明はない**(次章)
- **「インターネットを置き換える」は長期目標であって現状ではない**

## 第4部 深掘り — アーキテクチャの本質的な強さと限界

### 強み 1: 状態が「局所」に留まる

ルーティングテーブルは存在せず、ノードが持つのは「自分のツリー座標 +
キャッシュ済みの相手座標 + 直接ピアのブルームフィルタ」。グローバル
トポロジを誰も知らないにも関わらず届く、というのが Yggdrasil 由来の
美的強み。ノードの参加・離脱・リンク断は局所的な再計算で済む
(OSPF 型の全域収束が要らない)。

### 強み 2: トランスポート不可知論が徹底している

「上に TCP でも下に Bluetooth でもプロトコルが同じ」というのは
Reticulum 的な思想であり、将来の媒体(ラジオ、衛星、QR コードの
バケツリレー)にも適合する。これが「インターネットの代替」を目指す
資格を与えている。

### 強み 3: 身元の一本化

npub 一つで (a)ルーティングアドレス (b)Noise セッション相手 (c)Nostr
署名者 (d)課金対象 (e)アプリ層の相手 になる。既存インターネットで
この5つは IP・TLS 証明書・ドメイン・アカウント・支払い情報という
**5つの別レイヤに分散していた**。FIPS はこれを鍵一つに畳む。

### 限界 1: 単一スパニングツリーの構造的弱さ

ルート選挙は「最小 NodeAddr がルート」なので、**ルートは事実上ランダムな
誰か**になる。ツリー品質は運次第で、深いツリーほど座標が長く、
パスストレッチ(実最適経路との乖離)も大きくなりやすい。障害時は
再計算の間に到達不能期間が生じる。Yggdrasil も共有する課題で、
FIPS はコスト感応の親選択やフラップ抑制で緩和はするものの、
**「数十ノードのコミュニティメッシュ」以上への実証はまだ無い**。

### 限界 2: 座標発見のレイテンシとブルーム FPR

初回通信や回復時には LookupRequest→LookupResponse の
ツリー内ブルーム誘導探索が必要で、これは直接到達より常に遅い。
ブルームフィルタの偽陽性は不要な転送を生む(サイズクラス v1 = 1KB
フィルタに固定、誤り率は成員数に依存)。高頻度の座標発見が重なった
ときの輻輳制御も定量化されていない。

### 限界 3: パーミッションレス = Sybil 表面積

誰でも入れることは、誰でも中継ノード・advert 発行者・ポート広告者に
なれること。現状の防御は署名・起動エポック・ファイアウォール・リンク
品質メトリクスだが、**経済的シビル対策やレピュテーション機構は
プロトコルに存在しない**。悪意の中継が「届かないふり」をしても、
それを区別する強い仕組みは今のところない(これはインセンティブ設計の
未解決問題であり、nostr-vpn の支払い付き出口ノードが最初の実験)。

### 限界 4: エコシステムの二頭立て

issue #140 が示す通り、本家とフォークは「同じワイヤーの別実装」まで
分化が進み、ワイヤー仕様の単一の正典は存在しない。番号空間の
先取り競合(レポート 04)はこのガバナンス欠如の症状。プロトコルを
「複数実装の共通資産」に昇格できるかは、**キャパビリティ・ネゴシエー
ションとポートレジストリの公式化ができるか**にかかっている。

### 限界 5: 数学的検証・監査の不在

実績のあるアルゴリズムを組み合わせているとはいえ、**この合成物自体の
形式的解析・第三者監査はない**。特に Noise 方言・セッション状態機械・
ツリー動態の相互作用は、実装を通じた検証(両実装の cross-impl テスト、
fips-tcp の smoltcp オラクル、fips-ts の共有ベクタ)に依存している段階。

## 第5部 「いつ FIPS が正解か」— 実践的な判断軸

| 要求 | FIPS が強い | FIPS より適切な選択肢 |
|------|------------|----------------------|
| 少数の自前ノードを繋ぐ VPN | △(設定コストに見合うか検討) | Tailscale / WireGuard / Netbird |
| NAT 越えの鍵対鍵プライベート通信 | ✅ nostr-vpn | (Tailscale でも可だが管理サーバ要) |
| ISP 遮断時のコミュニティ網 | ✅ 独自性が高い | Yggdrasil / Reticulum / 802.11s + batman |
| ブラウザ・モバイル込みのメッシュ | ✅ mmalmi 系のみ | libp2p(重い) / WebRTC 自作 |
| Nostr エコシステムとの統合 | ✅ 独壇場 | — |
| 匿名通信 | ❌ | Tor / I2P / Lokinet / mixnet |
| 高信頼・大規模サービス網 | △(実証不足) | 通常の BGP/クラウド |
| 超低遅延のゲーム・メディア | △(座標探索とストレッチ) | 直接 WireGuard/QUIC |
| 「鍵=住所」の分散アプリ基盤 | ✅ | libp2p(peer ID 同等だが複雑) |

**要するに**: 「Nostr を既に使っている / 中央集権に依存したくない /
物理的にインターネットに依存できない」が一つでも当てはまるなら、
FIPS は現時点でほぼ唯一の成熟した選択肢になる。そうでないなら、
通常の VPN や分散基盤の方が実績も運用知見も多い。

## 第6部 将来シナリオ — FIPS はどこへ行きうるか

### シナリオ A: Nostr 経済圏の下位レイヤ化(可能性:中〜高)

Nostr が「SNS」から「分散サービスの PKI/台帳/支払い層」へ広がるなら、
その通信基盤として FIPS が選ばれる道筋がある。npub=住所=課金という
一本化は、nostr-vpn の出口ノード課金で既に実装例がある。
本家 issue #140 の調整が成立すれば、Nostr 標準(NIP)としての
「FIPS over Nostr」文書化もありうる。

### シナリオ B: レジリエンス網(災害・検閲対策)としての採用(中)

「インターネットが無くても動く」要件は増えている(災害、政府遮断、
辺地通信)。FIPS はこの用途で Yggdrasil/Reticulum と競合するが、
OpenWrt サポート・モバイル/ブラウザ実装・Nostr 連携で差別化できる。
ここで必要なのは実績の蓄積と、802.11s/LoRa など物理層の成熟。

### シナリオ C: 分岐したまま収束せず(中)

本家が「プロトコル仕様と実装」を再分割し、mmalmi 系が「製品向け
最適化実装」として並走する構図。ワイヤー互換が保たれる限り健全だが、
キャパビリティネゴシエーションが無いまま番号空間が衝突すれば、
「FIPS 準拠」が意味を失い、実装間で断片的に分断される。

### シナリオ D: 小規模コミュニティに留まる(現状)

現状は D。実装は活発だが、ユーザーベース・第三者監査・運用知見・
相互運用のエコシステムはまだ芽吹いたばかり。

### 打ち手(採用者として)

- **短期**: 目的限定(Nostr 連携 VPN・ブラウザメッシュ・鍵対鍵通信)で
  mmalmi 系を exact pin で採用。DataPacket + アプリポートに限定。
- **中期**: 混在メッシュでの相互接続テストを CI に組み込み、
  拡張機能への依存を隔離。本家 upstream のレジストリ調整をウォッチ。
- **長期**: 「FIPS v1 仕様」の単一正典化(issue #140 の行方)を支援する
  側に回るか、自前で最小仕様サブセットを切り出して仕様書を持つ。

## 第7部 結論 — この技術を一言で

FIPS は、**「インターネットを構成する根本の約束事 — アドレスは誰かに
割り当ててもらうもの、信頼は誰かが保証するもの — を、自分の鍵一つで
始められるネットワーク」**に置き換える試みである。新規性は個々の
アルゴリズムではなく、Nostr 鍵という「既に人々が所有し、名声を蓄積
している資産」をネットワークの PKI と住所台帳に転用した点にある。
Yggdrasil 以来のメッシュ理論と WireGuard/Noise の作法を土台に、
レジリエンスと脱集中を兼ね備えた「インターネットの外側に張れる
もう一つのインターネット」として最も実用に近い候補の一つであり、
mmalmi フォークはそれを製品レートに押し上げた流れの最前線。

ただし現時点の FIPS は「コミュニティメッシュと鍵指向アプリの基盤」で
あり、「インターネットの代替」はまだ設計意図であって実績ではない。
採用は目的限定・バージョン固定・共通サブセット運用が前提条件。

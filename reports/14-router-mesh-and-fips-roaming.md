# レポート14: ルーター自動メッシュと `!FIPS` ローミング — FIPS が狙う「5G ライクな市民網」の内部構造

**日付:** 2026-09-25
**対象:** jmcorgan/fips の OpenWrt パッケージが提供する 802.11s バックホールと `!FIPS` オープン SSID アクセス層。一次資料として本家リポジトリの how-to ドキュメント群(`docs/how-to/set-up-80211s-mesh-backhaul.md`、`set-up-open-access-ssid.md`)と Origami74 の Q3 レポートを突合した。

## 0. TL;DR

FIPS には2つの「物理網」機能が存在し、役割が厳密に分かれている。

- **802.11s バックホール**(ルーター⇄ルーター): OpenWrt ルーターがケーブルなし・AP なし・共有秘密なしで互いに無線リンクを張る。あえて**暗号化なし(open)+ HWMP 転送オフ**で、ルーティングと暗号は全部 FIPS の層に任せる設計
- **`!FIPS` オープン SSID**(ルーター⇄クライアント): 全ルーターが同名のオープン SSID を出し、スマホ/PC は「1回保存すれば全ルーターにローミング」する Freifunk 型モデル。**802.11r のような L2 モビリティ機構を使わず、FIPS のオーバーレイ身元(pubkey→メッシュ IPv6)がモビリティのアンカー**になる

この2層を合わせると「基地局(=FIPS ルーター)が無線で互いに繋がり、端末(=電話)がその間を歩き回る」構造になる — つまり**セルラー(5G)の形を、免許不要の市民設備で再現する試み**である。これが Origami74 が「cellular-like roaming」と呼ぶ応用であり、レポート13 の `!FIPS` 近接網(D-11/D-12)のさらに外側にある本丸である。

## 1. 802.11s バックホール — 「ルーターを置くだけでメッシュになる」機構

### 802.11s とは(前提)

802.11s は IEEE 802.11 Wi-Fi 標準の一部として定義されたメッシュモード。通常のインフラモード(端末=AP のスター型)と違い、**同格のメッシュポイント同士が互いにピアリングし、フレームの中継を行う**。対応ドライバ(ath9k/ath10k/mt76 = 市販 OpenWrt 機のほぼ全域)を持つルーターなら専用装置なしで動く。アマチュア無線・コミュニティ網の世界では Freifunk/Gluon が十数年前からこの上で BATMAN-adv を回してきた実績領域。

### FIPS 流の設計: あえて「薄く」使う

FIPS の 802.11s 設定は、通常の 802.11s 運用と意図的に2点違う。

**(a) `encryption none` — 無線層は無暗号化。**
乱暴に見えるが、論理は明快: FIPS のピアリンクは Noise IK ハンドシェイクで既に認証+暗号化されている。L2 で SAE(802.11s の共有鍵認証)を入れても二重化になるだけでなく、

- ルーター群へ共有秘密を配るプロビジョニングコストが発生する
- ath10k では SAE がファームウェアを低速の raw Tx/Rx モードに落とす(性能劣化)

という実害がある。そこで「open にして誰でもピアリング可能にし、各リンクは Noise ハンドシェイクが認証する」— **発見(mDNS/BLE)と同じ「広告はヒント、握手が認証」モデル**を電波にまで拡張している。なりすまし・MITM は鍵で防ぎ、「誰がピアになってよいか」はゲートしない(デーモンの max-peers 上限まで誰でも)。

**(b) `mesh_fwding 0` — 802.11s 自身のルーティング(HWMP)を殺す。**
これが重要な設計判断。標準 802.11s では HWMP(Hybrid Wireless Mesh Protocol)がメッシュ内で「誰を経由してどこへ届けるか」を自分で計算する。FIPS はそれを**切り、802.11s を「近隣への素のイーサーフレーム配達」だけに縮小**し、ルーティングは FIPS のスパニングツリーに一本化する。理由: 二つのルーティング層が共存すると互いに殴り合い、ブロードキャスト発見ビーコンがメッシュ全域に氾濫して「直接の隣人だけに届くべき情報」が壊れるから。

要するに **FIPS にとって 802.11s は「ケーブルのないイーサネット」以上ではない**。無線メッシュの賢さは使わず、賢さは全部 FIPS 側で持つ。トランスポート層設計書でも位置づけは同じで、イーサネットトランスポートは「同一セグメント上の複数 MAC アドレスへデータグラムを運ぶ媒体」としてしか見ていない。

### セットアップの実際

OpenWrt パッケージには `fips-mesh-setup` ヘルパが付属し、手順は驚くほど短い:

```sh
fips-mesh-setup radio1    # radio ごとに1回
```

これだけで mesh ID `fips-mesh`・暗号化なし・HWMP オフのメッシュ I/F が生え、`fips.yaml` に同梱済みの `transports.ethernet.meshN` エントリが I/F を自動でバインドする。**インタフェースは「現れた瞬間」にバインドされ、デーモン再起動すら不要**(逆に設定値を変えた場合のみ再起動)。

唯一のハードな落とし穴が**チャンネル**:

- メッシュポイントは同一チャンネルでしかピアリングしない。`channel 'auto'`(多くの機種の既定)だと各ルーターが勝手なチャンネルを選び、**メッシュが静かに一生形成されない**。全バックホール機で固定が必須
- DFS チャンネルは CAC で ~60 秒送信待ちが入るので非 DFS(5GHz なら36-48)推奨
- 同じ無線機に STA(クライアント上り)が居ると STA がチャンネルを握る — 上り回線を追う旅ルーター系と固定チャンネルメッシュは同一無線機で共存不能

デュアルバンド機では両帯域をメッシュに入れられるが、注意点として**フェイルオーバーであってマルチパスではない**: FIPS は1ピアにつき1アクティブリンクしか保持せず、2.4GHz(遠くまで届く)と 5GHz(高速)は相互の待機系になる。

### 制約まとめ

- **クライアント(電話・ノートPC)は 802.11s に入れない**。802.11s 参加はルーター/メッシュポイント間のみ。クライアントは次節の `!FIPS` AP か BLE 経由
- 同一無線機上の AP と mesh はエアタイムを共有し、単一無線のマルチホップはホップ毎におおむね半減する
- 電波は損失する: 802.11s ピアリングが「成立」していてもフレームの何割かは届かない — 有線にはないリンク品質概念が出てくる

## 2. `!FIPS` オープン SSID — クライアント用アクセス層

### 構造

全 FIPS ルーターが同名のオープン SSID `!FIPS` を自分の AP 無線から出す。これが「同じ SSID + 各ルーター独自 BSSID」= **標準的な ESS(Extended Service Set)** であり、クライアントは1回ネットワークを保存すれば**世界中のどの FIPS ルーター間でも標準の ESS ローミングで移動する**。「Freifunk モデル」と明記されている。

先頭の `!` は小技: アルファベット順のネットワーク一覧で先頭に来るようにするため(iOS/デスクトップOS。Android は信号強度順)。名前自体の一部で、SSID 一致はバイト完全一致なので `FIPS` とは別物。

### なぜオープンなのか(これも意図的)

- クライアントは「SSID + セキュリティ種別」で保存ネットワークを識別する。**一台でも PSK や OWE にすると同じ `!FIPS` 名が別の「保存ネットワーク」に分裂し、ローミングが壊れる**。オープンは「プロビジョニングがゼロの唯一のセキュリティ種別」
- OWE(Enhanced Open)も今は除外 — OWE-transition モードがクライアントベンダー間で一貫しないため
- 敵対者がアソシエイトして Noise ハンドシェイクまで成立するのは設計通り。**敵を止めるのはハンドシェイクではなく隔離ゾーン**(後述)
- ルーター側が「無差別オープン」になる代わり、身元・暗号・MITM 防止は FIPS 層の Noise IK が担保する

### アドレッシングの工夫(ローミングの要)

- **DHCPv4 は `10.21.<N>.0/24` を全ルーター共通で配る**(`N`=無線機番号、`2121` は FIPS ポート由来の語呂)。全ルーターが同じサブネットを配るので、**ローミングした電話はリースを保持したまま別ルーターへ渡り歩く**。dnsmasq の authoritative モードで、別ルーターが発行したリースの renew も新ルーターが ACK する
- IPv6 側は ULA プレフィックスを odhcpd が広告し SLAAC だけ(DHCPv6 は切る)。これは **Android のプロビジョニングチェック対策**でもある: RA か DHCP オファーが無いと Android は「ネットワーク無し」と判断して切断してしまう
- 全て「WAN があってもなくても動く」。ローミングはあくまでクライアント駆動(BSSID ホップは端末が決める)で、802.11r/k/v のような高速移行機構は使わない — **モビリティのアンカーは IP ではなく FIPS のオーバーレイ身元**なので、L2 移行でのアドレス継続性が本来要らない設計

### 隔離ゾーン(セキュリティの実体)

`fips_ap` 専用ネットワーク+ファイアウォールゾーンがあり、

- `br-lan` へのパスなし、WAN への転送なし
- 受け入れるのは DHCPv4・ICMPv6(SLAAC 用)・mDNS・FIPS トランスポートポートのみ
- AP クライアント分離 ON — 同じルーターにぶら下がる 2 台の FIPS 電話も L2 では直接届かず、オーバーレイ経由で通信
- 生イーサネットトランスポート(EtherType 0x2121)は IP ではなくファイアウォールを通らない

つまり「誰でも入れるが、入っても FIPS オーバーレイ面にしか触れない」。ここにホットスポット化(=WAN への転送)を足すと全部崩壊するので、フォワーディング追加は禁止事項。

### 「インターネットがない」は仕様

接続すると必ず「インターネットなし」警告が出る — これは**設計された定常状態**:

- 初回だけ「接続を維持/次から聞かない」を選択すれば全ルーター共通で記憶される
- 以後は「connected, no internet」のままアソシエイトを維持し、**モバイル回線が引き続きデフォルト経路**になる
- FIPS アプリだけが明示的に Wi-Fi 側へソケットをバインドするので、通常アプリは `!FIPS` の存在に気づかず、メッシュ通信だけが静かに Wi-Fi 経路を通る

## 3. 2層の組合せが「5G ライク」になる論理

| セルラーの概念 | FIPS 版での対応物 |
|---|---|
| 基地局(eNB/gNB) | 各 FIPS ルーターの `!FIPS` AP |
| 基地局間のバックホール(光ファイバ/PTMP) | 802.11s メッシュ(無線・ケーブル不要) |
| 端末のハンドオーバー | 端末主導の ESS ローミング(BSSID ホップ) |
| セルラー網内での端末識別(IMSI/SUPI) | FIPS の npub → メッシュ IPv6(オーバーレイ身元) |
| 移動しても継続するセッション | オーバーレイ身元がアンカーなので、L2 移行を通じても FIPS セッションは生き続ける |

この対応関係が示す構造的な強みは、**モビリティを「網側が面倒を見る」のではなく「身元が継続するので勝手に追従する」モデルに変えたこと**にある。セルラーのハンドオーバーは基地局同士がコンテキストを受け渡す複雑なシグナリングだが、FIPS では「どのルーターに繋がっても身元は同じ `npub1…` → 同じ `fd..` アドレス」なので、ローミング後の再認証や継続性を特別な機構なしで済ませる。欠点は L2 の隙間(ホップ中の短い切断)で、802.11r を入れない限りは発生する。

## 4. Android/fips2go の位置づけ — 「電話はクライアントであり、また橋になる」

Q3 レポートが特に強調しているのが、**Android は 802.11s をサポートしない**という制約を fips2go のようなアプリが逆に利用する点だ。

- Android の電話は 802.11s メッシュポイントにはなれない。802.11s 対応は概ねルーター/Linux の世界
- その代わり Android には **Wi-Fi Aware(NAN)** と **Wi-Fi Direct** がある — 電話同士の P2P 電波
- そして **`!FIPS` AP への接続** ができ、さらに `node.rendezvous.lan`(mDNS/DNS-SD)でそのルーター上の FIPS デーモンを発見する

結果として電話は**「AP 接続」と「Wi-Fi Aware 直結」の両方を持つノード**になり、Origami74 が指摘するように「Android が直接入れない 802.11s 網に、AP 経由で繋がった電話がブリッジになる」— **fips2go がトランスポート融合の装置**になる。これはレポート13 で「任意アプリを住民にする」と書いた点の、さらに物理層での補強である。

我々の実測(付録B 追補)で確かめた mDNS 発見がオフ・Bluetooth 代替が未検証だった点は、この設計文脈だと意味がはっきりする: **エミュレータ上では `10.0.2.2` 手動ピアで済んだが、実機の `!FIPS` 体験は「AP に繋ぐ → mDNS で発見 → Noise ハンドシェイク」の流れを想定している**。`fips-ap-setup` が唯一変更するデーモン設定が `node.rendezvous.lan: enabled` である点が、電話側の発見経路が mDNS であることを裏付けている。

## 5. SEC-08 での実演 — 何が「動いた」のか

Origami74 のレポートで報告された実演を要件別に分解すると:

| 実演 | 構成 | 意味 |
|---|---|---|
| 建物内で実メッシュ | 802.11s 対応ルーター群を OpenWrt + FIPS で配置 | ルーターを置くだけで相互リンクが立つことを確認 |
| 巨大アンテナ皿で隣アパートへ | 802.11s リンクを建物→アパートの長距離無線に伸ばす | 「イーサのみで」隣アパートのノードと接続でき、ping も実用域 — メッシュの到達範囲が1建物の中に閉じないことを実証 |
| 電話の融合 | Android は 802.11s 非対応なのに AP 接続で mesh に参加 | クライアントとバックホールの橋渡しが機能することを確認 |

注意点として、ここで確認されたのは**無線の到達とトランスポートの成立**であり、「スマホが歩き回ってローミングする」状態そのものの実演報告ではない。同時に、多トランスポート(BLE+Wi-Fi Aware、あるいは無線+有線ケーブル)で発生したリンクのバタつきは `fips#167`/`myco#50` で対処中とある — **実環境で「ルーターを置くと必ず安定メッシュになる」段階ではまだなく、複数経路が同時に見える環境ほど不安定になる残課題がある**。

## 6. 先行技術との対比 — これは何と違うのか

| 既存技術 | やっていること | FIPS 流との違い |
|---|---|---|
| **Freifunk / Gluon(BATMAN-adv)** | 802.11s 上で L2 メッシュを運営、オープン SSID で市民網 | ルーティングは BATMAN-adv(L2 メッシュプロトコル)。**FIPS は HWMP すら切り、ルーティングは FIPS 自身のスパニングツリー**。発見・認証・暗号は全部 Noise IK |
| **802.11r/k/v(高速ローミング)** | エンタープライズ Wi-Fi の標準移行。AP 間でコンテキスト受け渡し | FIPS は L2 移行機構を使わない。身元がオーバーレイにあるので再認証をそもそも必要としない。AP 側の設定が不要 |
| **Yggdrasil / cjdns** | IPv6 ベースの暗号化オーバーレイメッシュ | 似た理念だが、FIPS はトランスポート非依存(UDP/TCP/Ethernet/BLE/mDNS を全部吸収)。物理層の自動メッシュ化まで含む |
| **セルラー(4G/5G)** | 免許帯域・大規模インフラ・国家系識別 | 「電波は開けて、身元と暗号はオーバーレイに持たせる」ことで、免許も契約もない市民版を目指す。ただし QoS・干渉管理・移動体のハンドオーバー品質はセルラーには到底及ばない |
| **Hotspot 2.0 / Passpoint** | キャリア Wi-Fi への自動ローミング | 事業者間ローミング協定が前提。FIPS は「協定」ではなく「同じ SSID 名」という慣習だけで成立する |

端的には: **「L2 のインテリジェンスを全部捨てて、身元・認証・ルーティングをオーバーレイに集約した」**点が FIPS 独自の設計であり、それが「AP を1台置けば勝手にメッシュの一員になる」シンプルさを生んでいる。

## 7. 未解決・オープンな課題

- **マルチトランスポート競合**: BLE+Wi-Fi Aware のように複数媒体で同じピアが見えるとリンクがバタつく(fips#167 で対策中)。802.11s+有線も同じ問題を引き起こしうる
- **クライアントのローミング体験**: 802.11r が無いので BSSID ホップ中に L2 の隙間がある。ビデオ・音声通話には影響する可能性
- **802.11s はクライアントを受け入れない**: スマホ・PC は AP か BLE 経由のみ — 802.11s 対応が広がるかはチップ依存
- **同一 SSID という規約の脆弱性**: 「`!FIPS` を出せば誰でも参加できる」が強みであると同時に、**悪意ある同名 SSID**(Evil Twin)が任意に置ける — ただし接続しても Noise IK が必ず各リンクを認証するので、成りすましは通らない。被害範囲は「`!FIPS` に繋いだら別の誰かの網だった」まで
- **単一無線機の帯域半減**: メッシュホップ毎に throughput が減る。実運用はデュアル/トライバンド前提

## 8. まとめ — これが「nvpn にはない」どころか「そもそも存在しない種類」の応用である理由

- **nvpn(nostr-vpn)** は「あなたのデバイスを、あなたのロースターに基づいて網に入れる」プライベート VPN。網を張る主体はユーザーであり、網の提供側としては「自分のデバイス間を繋ぐ」ことしか目的にしていない
- **`!FIPS` + 802.11s メッシュ**は逆に「**網の提供側になる**」装置だ。ルーターを置けば「基地局」になれ、電話はその間をローミングする。ユーザーの網ではなく**誰かが運営する市民網にあなたが加入する**形
- Origami74 が TollGate(課金レイヤー)と組み合わせる方向を描いているのもこの延長で、**「市民が置いたルーターが、通過するデータ量を自動課金する」という携帯電話網のオープン版**を構想している

レポート13 で「fips2go が電話をメッシュ住民にする」ことを確認したが、本レポートの領域はそのさらに外側 — **「ルーターを置く人が網のオペレーターになり、電話がその網の中を歩き回る」**という、FIPS プロジェクトが最終的に狙っている「国民網」の形である。

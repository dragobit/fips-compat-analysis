# 05. mmalmi 系 FIPS ライブラリ採用可否判定

**質問**: 「プロジェクトとして mmalmi の方の fips 系ライブラリを使っても大丈夫か」

## 判定: 条件付きで「使える」— ただし本家ではなく「nostr-vpn エコシステム」を選ぶ決定として

### 使える根拠(安心材料)

| 観点 | 評価 |
|------|------|
| ライセンス | MIT(mmalmi/fips, fips-ts)、0BSD(fips-tcp) — 法的障害なし。本家由来部分も MIT で帰属表示も保持 |
| 出荷実績 | nostr-vpn が製品として出荷中(iOS App Store / Android / StartOS / Umbrel、GitHub 1,159★)。自社製品で使い倒されているコード |
| パッケージ公開 | `nvpn-fips-core` `nvpn-fips-endpoint` `nvpn-fips-identity` `nvpn-fips-tcp` `nvpn-fips-tcp-endpoint` が crates.io に公開済(最新 0.4.82/0.2.x)。`cargo install` で素直に入る |
| ワイヤー互換 | レポート 02 の通り本家と FMP/FSP v0 でバイト互換。混在メッシュでも基本的に通信できる |
| テスト文化 | fips-ts は Rust との**ライブ相互接続テスト**(Noise レスポンダを stdio 駆動)、fips-tcp は smoltcp オラクル + 共有 JSON ベクタ + 双方向 Rust↔TS interop。検証姿勢は堅い |
| 性能 | データプレーン書き換えの効果は本家 issue で定量的に提示済(約 3x スループット) |
| 機能範囲 | WebRTC/WebSocket/ブラウザ/モバイル回復など、本家に無い**Web 系ユースケースの必須機能**を持つ |

### リスク(条件付きである理由)

| リスク | 度合 | 備考 |
|--------|:---:|------|
| 実質単一メンテナ | 高 | mmalmi 系は全リポ Martti Malmi 単独(+自動生成コミット)。バスファクタ 1。ただし nostr-vpn が製品依存しているため放置リスクは低め |
| API 不安定 | 高 | すべて 0.x。フォークはリリースを数日単位で回し、nostr-vpn 自身が `=0.4.82` の完全一致ピンで防御している — **こちらも exact pin 必須** |
| npm 未公開 | 中 | `@fips/*` パッケージは npm 無し。`fips-tcp/ts` は dist を git 追跡して git revision ピン推奨。タグ `runtime-v0.0.42` 等で固定可能だがサプライチェーン的に脆い |
| 上流との未調整 | 中 | issue #140 未回答。ポート/msg_type の番号空間は mmalmi が事実上先取り。本家が「同じ FIPS」として進化しても追随保証なし |
| 本家機能の欠落 | 中 | Nym/SOCKS5/ネイティブプロセス API/OpenWrt/gateway はフォークに無い。それらが必要ならフォークでは不足 |
| セキュリティプロセス | 中 | mmalmi/fips に SECURITY.md 無し。本家はあり。脆弱性報告の導線が不明瞭 |
| 監査 | 中 | どちらの実装も第三者セキュリティ監査の記録なし。暗号は Noise ベースだが独自方言(レポート 02)なので「標準 Noise 監査済」とは言えない |
| 将来の再統合 | 低〜中 | #140 が「フォーク採用」に転ぶと本家コードベースが入れ替わる;「並行維持」でもレジストリ調整が必要。いずれにせよワイヤー v0 の維持は両者の共通利益 |

### ユースケース別の推奨

| あなたのプロジェクトの要件 | 推奨 |
|---------------------------|------|
| ブラウザ/TS クライアントが必要 | **mmalmi 系を選ぶしかない**(fips-ts しか選択肢が無い) |
| WebRTC/WebSocket トランスポートが必要 | 同上 |
| Rust で安定 API・上流正統性重視 | **本家 jmcorgan/fips** を git 依存で |
| 高スループット VPN 系 | mmalmi(nvpn-fips-*)。nostr-vpn と同じピン戦略で |
| 単なる「FIPS 上の信頼バイトストリーム」 | `nvpn-fips-tcp` (0BSD)。FIPS 本体実装の選択とは分離可能 |
| 本家・フォーク混在メッシュ | 可能だがレポート 04 のガードレール遵守(H-1/H-2) |

### 採用する場合のチェックリスト

1. **バージョン完全固定**: Cargo.toml は `fips-core = { package = "nvpn-fips-core", version = "=0.4.82" }` のように `=` ピン。TS は git タグ/コミットピン
2. **相互接続テストを CI に**: 自プロトコルで使うメッセージ型の範囲で、本家実装とのハンドシェイク+エコーを定期的に検証
3. **必須依存を共通部分に限定**: DataPacket/ポート 1024+ に留め、EndpointData/port 257/direct-FSP はオプション機能として隔離
4. **Nostr advert には注意**: webrtc/websocket エンドポイントを公開する場合、本家ノードから見えなくなることを理解した上でスコープを分ける
5. **git.iris.to を正本として扱う**: GitHub はミラー。issue/リリースの正本は Nostr 上の git.iris.to リポ(npub1xdhnr9...)
6. **フォーク可能な心構え**: ライセンス上は完全にフォーク可能。上流が止まった場合の保守体制を内部で決めておく

## 総合評価

mmalmi 系は「本家の派生」というより **nostr-vpn が駆動する並行実装群**であり、
品質・テスト・実用性は本家と同等以上の領域がある。採用の実質的リスクは
技術ではなく**ガバナンス**(単一メンテナ・番号空間未調整・本家との関係未決)
に集中している。これらは exact pin + 混在時の共通サブセット運用 +
CI interop テストで十分に管理可能であり、**Web/ブラウザ系で必要なら採用は
正当化できる**。純 Rust・上流追随重視なら本家を選ぶべき。

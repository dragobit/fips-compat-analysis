## ケース 21: サーバーレス P2P Web アプリ(fips-ts)

### 何をするか

ブラウザ上の Web アプリ同士が、**サーバを立てずに互いの鍵宛てで通信**する。
ログインもドメインも API サーバも要らない — 「npub を知っている相手に
直接話しかける」だけ。

### 構成

```
[ブラウザA(fips-ts)] ←→ [ブラウザB(fips-ts)]
        ↑                     ↑
   WebRTC データチャネル / WSS ピア経由でメッシュに参加
   (FSP セッションはエンドツーエンドで鍵宛て)
```

- fips-ts の FSP/トランスポート層を JS アプリから直接利用
- WebRTC をトランスポートにしてブラウザ間の直接リンクを張れる
  (mmalmi fips の `webrtc` overlay kind が該当)
- WebRTC シグナリングは「接続先の座標交換」に使い、
  実際の通信は FIPS セッションに載せる

### 実現するもの

- **チャット/共有/コラボ**を「URL と自分の鍵」だけで開始
- ファイル・画面・同期データを**仲介サーバを経由せず**転送
- 「この npub にだけ見える」公開範囲の個人 Web アプリ
- ブラウザが FIPS メッシュの第一級ノードになる —
  デスクトップ/モバイル/埋込みと同じ世界に参加

### 現状の注意点

- **@fips/* パッケージは npm 未公開**: git ピン(dist も追跡されている)
  か、ソースからの直接利用が前提
- **Rust 側との互換は「FIPS Noise 方言」を忠実実装**している
  (fips-ts/docs/rust-compat.md による検証済み)が、
  リポジトリ上の仕様書には細かい誤記がある(別レポート 02)
- ブラウザに常駐してメッシュを保つ負荷・再試行・UI 表示はアプリ側の責任

## ケース 27: 農業・気象・野生動物のセンサー網

### 何をするか

畑・牧場・山間部・国立公園など広いフィールドに散らばった
センサー(温度・湿度・土壌・水位・動物タグ・カメラ)を
**ローカルメッシュで集約し、上流に1点だけ出口を持つ**構成。

### 構成

```
[センサーノード(BLE/Wi-Fi/802.11s)] → [集約ノード群] → [出口ノード]
                                          (域内メッシュ)      (衛星/携帯/長距離)
```

- **域内は完全ローカル**: センサー間・センサー↔集約ノードは
  BLE/Wi-Fi/Ethernet のいずれかでメッシュ化
- **上流出口は1点だけ**: その出口ノードにだけ外部回線を挿せば
  網全体が外部へ出られる。出口が複数あれば冗長化
- **鍵=各センサーの身元**: 各ノードが npub を持つので、
  「この温度値はどのセンサーから来たか」が暗号的に確か

### 実現するもの

- ハブ・ゲートウェイ・専用プロトコル(LoRa/Zigbee 等)に縛られず、
  **IP レベルのセンサー網を Wi-Fi/BLE のまま構築**
- センサーが Nostr イベントとして署名された測定値を出せば、
  上流側の集約・表示・長期保存が「署名済みデータ」で統一される
- フィールド内の機器(灌漑バルブ、給餌器、カメラ)を
  鍵宛てのコマンドで遠隔操作

### 留意点

- BLE は極端に帯域が細い。測定値程度なら良いが、画像・音声は
  Wi-Fi/Ethernet 側のリンクを通る構成が必要
- 長距離・屋外型のリンクは FIPS 自体ではなく別の無線設計
  (長距離 Wi-Fi、LoRa、衛星)が担当。FIPS はその上の「網の形」
- センサー側の消費電力設計が本質(メッシュ参加の維持コストは
  バッテリー運用を圧迫しうる)

## 関連ケース(簡潔)

### 26. ドローン・ロボットの遠隔操縦リンク

- ロボット自体が FIPS ノードになり、Wi-Fi 直結 + メッシュの
  複合で「現場の近く」と「遠隔の操作者」を繋ぐ
- 現場内では BLE/Wi-Fi メッシュ、上流はモバイル回線や衛星 —
  どこからでも「そのロボットの npub」に届く
- 複数台のロボット同士を協調させる時も「npub 同士の会話」で抽象化できる

### 24. モバイル・デスクトップ両対応のチャット/共有アプリ基盤

- fips-ts(JS)+ fips-core(Rust)の双方から同じ FSP で話せるので、
  **一つのプロトコルでブラウザ・ネイティブ・組込みを貫通**
- 「アプリの中にメッシュを内蔵する」設計が可能

## このグループの要点

| 対象 | 使う層 | 答えは |
|---|---|---|
| Web アプリ | fips-ts | ライブラリ |
| センサー・ロボット | fips-core / fips-ts | ライブラリ+カスタム |
| ここに nvpn の出番は少ない | (製品ではなく基盤として使う) |

「製品としての VPN」ではなく「**自分のアプリに鍵宛て通信を内蔵する**」
ところがこの領域の本質。
